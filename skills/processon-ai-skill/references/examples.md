# 端到端示例

> 三个完整示例，用于对齐产出风格与交付话术。**示例内容为范例，非模板**：可沿用其流程与话术风格，不要照搬具体节点或措辞。
>
> 示例里的「内部执行」仅供 AI 参考，**这些内容不出现在给用户的回复里**。
>
> 示例链接中的 **`{BASE}` = 当前环境的站点根**（正式 / 灰度等，由 `PO_ENV` 或包内默认环境决定），实际交付时用后端返回的真实链接、或 `node scripts/get-token.mjs processon_env_info` 的 `LINK_*`；**`{CHANNEL}` = 本包对应的载体来源**（打包时已注入，读到即实际值）。**不得硬编码域名**。

## 示例一：新建流程图

### 用户输入

> 帮我画一个电商订单支付的流程图

### 内部执行

```
① 判断走哪条线 → 关键词「流程图」→ 流程图线
② category → 流程图 = flowbase
③ 在用户需求上补专业约束，得到这段内容：

   「电商订单支付流程：用户提交订单 → 校验库存 → 库存不足则提示并结束 →
     库存充足则生成支付单 → 用户支付 → 校验支付结果 → 成功则更新订单状态并通知发货 →
     失败则释放库存并提示重试。要求：明确开始/结束节点，决策点用标准菱形，布局清晰，避免线条交叉」

   通过 orchestrator.mjs 一条命令完成「生成 DSL → 落库」：

   node scripts/orchestrator.mjs category=flowbase title='电商订单支付流程' <<'POB64'
   电商订单支付流程：用户提交订单 → 校验库存 → 库存不足则提示并结束 →
     库存充足则生成支付单 → 用户支付 → 校验支付结果 → 成功则更新订单状态并通知发货 →
     失败则释放库存并提示重试。要求：明确开始/结束节点，决策点用标准菱形，布局清晰，避免线条交叉
   POB64

   → 脚本内部自动：b64 编码 → generatedDsl → 解析 DSL+reqId → b64 编码 → createProcessOnFile

④ 从返回取 chartId（内部留存）、文件链接、文件缩略图链接、消耗AI点数
```

### 给用户的回复

```

图形已生成：

- 文件名：电商订单支付流程
- 类型：流程图
- 文件链接：{BASE}/diagraming/6a1b2c3d4e5f6a7b8c9d0e1f
- 文件缩略图：{BASE}/chart_image/thumb/6a1b...png?cid=6a1b2c3d4e5f6a7b8c9d0e1f

**已在右侧浏览器已打开该文件，您可进行查看或编辑→→**

```

> 说明：全程没有提 DSL、没有说"正在调用生成接口"、没有展示 chartId；**落库成功后须用内置浏览器打开文件链接**，确认打开成功才**加粗**输出「**已在右侧浏览器已打开该文件，您可进行查看或编辑→→**」；**内置浏览器不可用时这句整句省略**，只保留链接与「可点击链接查看与编辑」。

## 示例二：新建思维导图（含内容加工）

### 用户输入

> 把这段会议记录整理成思维导图：
>
> 今天讨论了 Q3 的增长计划。市场部说获客成本比上季度涨了 30%，主要是投放渠道单一，
> 建议今年下半年拓展内容营销和私域。产品部提到留存率只有 42%，新用户第一周流失最严重，
> 打算优化新手引导流程，另外要把核心功能的入口做得更明显。技术部说现在的服务响应偶尔超时，
> 大促期间尤其明显，需要在 8 月底前完成一轮扩容和缓存优化。最后定了下季度三个重点：
> 降获客成本、提首周留存、保稳定性。

### 内部执行

```
① 判断走哪条线 → 「整理成思维导图」→ 思维导图线（不调 generatedDsl）
② 按方法论加工 Markdown：
   · 主题定锚 → 「Q3 增长计划」作为根节点
   · 按部门/议题做 MECE 拆解 → 三个部门 + 一组结论
   · 末级精炼 → 原文长句压成短语，不粘贴原文
③ structure → 内容是会议观点归纳、发散型 → mind_free
④ category → structure 有同名值 → mind_free
⑤ theme → 内容偏理性汇报 → 主题名「极简黑白」（AI 只选名，JSON 由脚本取）
⑥ 通过 mindcreate.mjs 一条命令完成「编码 → 取 theme JSON → 落库」：

   node scripts/mindcreate.mjs \
     category=mind_free structure=mind_free theme=极简黑白 title='Q3增长计划' \
     <<'POB64'
   <Markdown 内容原样写在这>
   POB64
   （脚本内部自动 b64 编码、取 theme 完整 JSON、直连 MCP 落库；不传 reqId、不调 generatedDsl）
```

### 加工后的 Markdown（作为 content）

```markdown
# Q3 增长计划

## 获客成本
### 成本环比上涨 30%
### 主因：投放渠道单一
### 改进方向
- 拓展内容营销
- 建设私域运营

## 用户留存
### 整体留存率 42%
### 流失集中在新用户第一周
### 改进方向
- 优化新手引导流程
- 强化核心功能入口曝光

## 服务稳定性
### 响应偶发超时，大促期间明显
### 8 月底前完成扩容与缓存优化

## 下季度三个重点
### 降低获客成本
### 提升首周留存
### 保障服务稳定性
```

### 给用户的回复

**顺序要求：先给文件信息与链接，Markdown 置于最后。** 内容篇幅可能较长，置于链接之前会削弱链接的可见性。

```

## 示例三：编辑（情况一，本地改文字）

> 承接示例一：同一会话里刚生成了「电商订单支付流程」，上下文中有该图的 DSL 与 chartId。

### 用户输入

> 把里面的"通知发货"改成"通知仓库发货"

### 内部执行

```
① 分流判断
   · 上下文有 DSL + chartId ✅
   · 改的是文字，不动逻辑结构 ✅
   → 情况一（本地改，不调 generatedDsl）
② 在上下文那份 DSL 里把"通知发货"替换为"通知仓库发货"，其余一字不动
③ 改完的 DSL 用 b64.mjs 编码，直接传入：

   node scripts/mcp-call.mjs updateProcessOnFile \
     chartId=6a1b2c3d4e5f6a7b8c9d0e1f \
     content="$(node scripts/b64.mjs <<'POB64'
<改完的 DSL 原样写在这>
POB64
)" title='电商订单支付流程'

   · 不传 reqId（未调 generatedDsl）
   · title 传原标题（改名不生效，本 Skill 不支持改标题）
④ 从返回取文件链接、文件缩略图链接
```

```

## 过程话术：最常见的越界表述

执行与交付过程中，「边做边报」最容易把内部细节漏给用户。核心要求是**内部细节一律静默**（见 `SKILL.md`「面向用户的输出规范」）：

| 错误写法 | 问题 |
|---------|------|
| 「这是简单的文字修改，属于情况一，我直接在原有 DSL 中修改后更新」 | 暴露内部命名、判断路径与实现细节；只应说「正在为你修改…」 |
| 「正在调用 createProcessOnFile 落库…」 | 暴露工具名与内部术语；只应说「正在为你生成图形…」 |
| 「正在读取主题配置…」「已取到主题样式」 | 暴露参数取值过程 |
| 「macOS 的 base64 参数不同，我用 Node.js 来正确编码内容」 | 暴露编码实现与系统差异；**换了做法也不必解释原因** |

> 其余反例（`content` 传明文、手工 / 系统 base64、curl 直连、绕过 `mindcreate.mjs` 手写 theme JSON、函数调用语法传参、打开缩略图链接、覆盖已有页签、漏掉或变体输出加粗提示语等）已在 `SKILL.md`「严格规则」的 MUST / NEVER 与「面向用户的输出规范」中列明，此处不再重复。
