# 思维导图生成 mindmap

> 把用户的自然语言 / Markdown / 长文本 / 文档 / 网页 / 图片文字等，加工成结构清晰、层级分明的**思维导图类**脑图，并通过 `createProcessOnFile` 落库到用户 ProcessOn 账号。

> **本文件为内部编排依据，对用户静默执行**（内部术语黑名单见 SKILL.md「严格规则」）；对用户只说「正在为你整理…」，完成后给 Markdown、结果与链接。

## 与流程图线的根本区别（务必先读）

思维导图**不产 DSL、不调用 `generatedDsl`**。内容由 AI 直接按下方方法论加工成 **Markdown**，再配 `structure` + `theme` 落库。

| | 流程图类 | 思维导图类（本文件） |
|---|---|---|
| 生成来源 | `generatedDsl` → DSL | **AI 直接写 Markdown** |
| content | DSL | 纯 Markdown |
| `reqId` | 必传 | **不传** |
| structure | 不传 | **必填**（mind_*，7 类） |
| theme | 不传 | **必填**（只传主题名，完整 JSON 由 mindcreate.mjs 内部取用） |
| category | 12 类（兜底 flowbase） | mind_*（5 类，**与 structure 不等同**） |

> **禁止**：思维导图任何环节都不得调用 `generatedDsl`。内容一律由 AI 本地加工。
> **`category` 与 `structure` 是两个不同的东西**，取值范围不同、各传各的，详见第二、二之二节。

## 适用范围

结构化整理、知识提炼、内容总结、信息归纳、框架生成、资料梳理、思维导图/脑图生成。用户提供或上传自然语言、Markdown、长文本、文档、网页、图片、书籍、论文、报告、会议记录等，希望快速理解、提炼、总结、拆解、沉淀为结构化知识时，走本线。

**不适用**：流程图、泳道图、时序图、系统架构图、ER 图、UML 图等流程或技术图表 → 走流程图线（`references/flowchart.md`）。

## 一、内容加工方法论（核心）

首要任务不是把文本换个格式，而是把各类文档/图片/零散信息转化为可理解、可复用、可编辑的结构化知识框架。生成结果兼顾**信息准确、结构清楚、节点精炼、适合浏览**。

### 分析与转化

- **目标优先**：先判断用户是要"快速看懂内容""提炼知识框架""形成汇报/学习/执行结构"，还是仅要某种指定图形。未指定时，默认服务于"内容理解与结构化沉淀"。
- **附件优先读取**：用户上传附件并要求"根据附件生成"时，必须先读取附件内容再生成 Markdown。PDF/Word/图片/扫描件先做文本提取或识别；无法读取时不要臆造，先说明限制。
- **文档/图片加工步骤**：
  1. **内容摄取**：识别材料类型与信息密度。文档抓标题、摘要、目录、段落主题句、结论、关键数据；图片识别文字、主体、标注、图例、方向、表格字段与显著关系。
  2. **主题定锚**：提炼唯一核心主题作为根节点，输出为一级标题 `# 标题`。
  3. **标题层级保留**：文档有明确目录/各级标题时原样保留骨架（层级 <5 级：把最后一层内容洞察提炼成一句话作为最后一级；层级 >5 级：第 5 级及之后洞察提炼成一句话作为第 5 级）。
  4. **末级内容精炼**：到最后一级标题下的正文时，若原文较长，**整合成一句话观点**或**提取最重要一句话**作为该节点值；严禁粘贴大段原文。
  5. **要点抽取**：围绕"结论、概念、步骤、分类、问题、证据、建议"提取高价值信息，删噪声/重复/低价值细节；多文档先合并同类项再去重。
  6. **关系建模**：识别层级、因果、时间、流程、并列、对比关系，优先形成便于理解复用的骨架。
  7. **框架压缩**：节点短句化、短语化、名词化，一个节点一个信息点。
- **结构化拆解**：基于 MECE（相互独立、完全穷尽）或清晰逻辑递进拆层；骨架层级忠实保留，仅末级正文精炼。
- **语义化映射**：一级主题 `#`；主要模块/章节 `##`；子模块/知识点/步骤/分类 `###` 及以下；解释性内容/参数/案例/清单用无序列表 `-`。
- **忠实与增强并重**：优先保留用户原文的核心观点、关键结构、事实边界，再做必要重组/压缩/优化；目录标题骨架高度忠实保留（不改层级归属和命名），仅末级正文精炼；信息不足时用通用保守表达，避免臆造。
- **结构选择**：按下方「二、图类型」表匹配；无法判断默认 `mind_free`。

### Markdown 输出约束

- **纯结果输出**：只输出最终 Markdown，不要"以下是生成结果"之类的说明，不要代码块包裹整篇。
- **层级连续**：不得跳级（不能 `#` 直接到 `###`）。
- **标题层级上限**：最多到 `######`；超过 6 级改用无序列表 `-`，不得再加 `#`。
- **禁止 HTML 标签**（除非在代码块内或作为字符串示例）。
- **忠实转化**：有原始文档时优先保留核心结构再优化。

### 内容卓越性（主动增强，辅助理解）

- **💻 代码块**：涉及代码/脚本/配置/命令行时，必须用标准代码块。
- **📐 数学公式**：涉及科学定律/数学推导/金融模型/算法公式时，用标准 LaTeX。
- **🖼️ 视觉插图**：文旅/美食/设计/自然科学/动植物/历史文化/儿童教育等适合图像的主题，可主动插入占位图 `- ![alt](https://loremflickr.com/800/600/关键词)`（1-3 张代表性图片；逻辑/技术/操作类可不加，优先结构清晰）。图片前不加空行或 `<br />`，直接写成同级列表项。
- **🚀 Emoji**：仅在能标识分类、区分层级、引导视线时使用（如 💻 代表电脑），必须帮助一眼看懂节点核心含义，严禁纯装饰堆砌。

### 对话式修改

采用**全量重绘**：用户提修改需求时，读对话历史，在之前 Markdown 基础上改，生成**全量更新后**的 Markdown，再走 create（或 update）重新落库。

## 二、structure 结构（7 类，布局形态）

`structure` 决定思维导图的**布局形态**。**严禁编造参数**，必须从下表精准匹配：

| 名称 | structure | 适用场景 |
|------|-----------|---------|
| 思维导图 / 中心放射 / 默认结构 | `mind_free` | 书籍文献章节结构拆解、头脑风暴与创意发散、主题灵感扩展、读书笔记发散整理、会议观点与零散信息归纳、知识体系分类。**默认/兜底** |
| 逻辑图 / 向右延伸 | `mind_right` | 方案大纲生成、工作总结提纲、汇报框架梳理、学习步骤与执行流程梳理 |
| 组织结构图 | `mind_org` | 公司组织架构设计、部门层级关系、团队岗位职责、人物谱系与上下级关系 |
| 鱼骨图 | `mind_ishikawa_left` | 问题根因分析、故障诊断、复盘归因、原因排查与改进方向分析 |
| 时间轴 | `mind_timeline_h` | 项目阶段规划、任务时间安排、里程碑梳理、事件发展过程与成长历程回顾 |
| 树形图 | `mind_tree_free` | 项目任务拆解、WBS 工作分解 |
| 树形表格 / 表格图 | `mind_treeTable_left_title` | 多方案对比分析、产品参数清单、层级数据表、分类汇总与结构化信息对比 |

**常见场景适配**：

- 内容偏发散、灵感、观点归纳、结构拆解 → `mind_free`
- 内容偏线性逻辑、提纲、步骤、流程 → `mind_right`
- 内容包含部门、岗位、人物上下级关系 → `mind_org`
- 内容用于分析问题原因 → `mind_ishikawa_left`
- 内容包含时间、阶段、里程碑、过程演变 → `mind_timeline_h`
- 内容需按层级展示表格化对比、参数清单或分类汇总 → `mind_treeTable_left_title`

> **结构兜底**：无法明确判断用哪一种 `structure` 时，默认传 `mind_free`。类型模糊时先问用户要哪种。

## 二之二、category 文件类型（5 类，与 structure 不等同）

`category` 是**文件类型**，取值范围与 `structure` 不同，当前 5 类：

| 图形类型 | category |
|---------|----------|
| 普通思维导图 | `mind_free` |
| 组织结构图 | `mind_org` |
| 树形图 | `mind_tree_free` |
| 鱼骨图 | `mind_ishikawa_left` |
| 时间轴 | `mind_timeline_h` |

**对应规则**：

- 所选 `structure` 在上表中有同名 category → `category` 传该同名值。
- 所选 `structure` 在上表中**没有对应**（即 `mind_right`、`mind_treeTable_left_title`）→ **`category` 统一传 `mind_free`**。

> 举例：用户要"汇报框架提纲" → `structure=mind_right`（布局匹配），但 category 无此项 → `category=mind_free`。
> `category` 与 `structure` 均为必填，各自独立传入。

## 三、theme 主题（AI 只选主题名）

AI 依内容、语气、场景，从下列 6 个主题中选最合适的一个：

| 主题名 | 色感 / 适合场景 |
|--------|----------------|
| 现代活力 | 四色分区、高频对比 |
| 复古单色 | 暮紫阶梯、克制深邃 |
| 极简黑白 | 无色系阶梯、高冷职业（**选不出时的默认**） |
| 柔和雅韵 | 灰绿单色、柔和理性 |
| 暗夜极光 | 极暗背景、荧光分支、酷炫前卫 |
| 浪漫治愈 | 樱花粉主色、明黄点缀、柔和甜美 |

**传参规则**：`theme` 只传**主题名**（如 `theme=极简黑白`）给 `mindcreate.mjs`；该主题的完整 JSON（约 1100~1300 字符）由脚本内部从 `references/mindmap_themes.json` 原样取用。

- AI **不提取、不手写、不转述、不打印 theme JSON**——值错了不会报错，会**静默生成错误样式**。
- 主题名固定为上表 6 个，不得臆造新名；选不出一律用默认「极简黑白」。
- `theme` 不做 base64；脚本内部直连 MCP，无需 `--no-coerce`，AI 无需处理。

## 四、调用形态（mindcreate.mjs）

> 思维导图线通过本 Skill 自带的 `mindcreate.mjs` 一条命令完成「b64 编码 → 取 theme JSON → 落库」。
> **Markdown 编码与 theme JSON 取值都在脚本内部完成，不经过 AI 上下文**；AI 只输出 Markdown、选定 structure / category / 主题名。
> **传参形式用 `参数=值`**；heredoc 定界符 `POB64` 用单引号包裹。

### 新建

```
node scripts/mindcreate.mjs \
  category=<mind_free|mind_org|mind_tree_free|mind_ishikawa_left|mind_timeline_h> \
  structure=<7 类之一，按第二节匹配；与 category 不必相同> \
  theme=<6 个主题名之一，默认 极简黑白> \
  title='<文件名>' \
  <<'POB64'
<Markdown 内容原样写在这，单引号 heredoc 不做转义/变量展开>
POB64
```

- **不传 `reqId`**：思维导图不经过 `generatedDsl`，无 reqId 可传。
- **不调用 `generatedDsl`**。
- `category` / `structure` 缺省时脚本兜底 `mind_free`，但仍应按第二、二之二节显式选准。

### 编辑（全量重绘）

加 `chartId=<目标文件id>`、`title='<原标题>'`，去掉 `category`，其余一致：

```
node scripts/mindcreate.mjs \
  chartId=<目标文件id> structure=<7 类之一，与原图一致> theme=<主题名> title='<原标题>' \
  <<'POB64'
<全量更新后的 Markdown 原样写在这>
POB64
```

> 编辑的分流判断与确认规则见 `references/edit.md`。

## 五、数据流转

1. 判断目标与图类型（模糊 → 先问用户）；读取附件/长文本。
2. 按「内容加工方法论」加工成 Markdown（骨架保留、末级精炼、MECE）。
3. 选 structure（第二节，默认 `mind_free`）→ 定 category（第二之二节）→ 选 theme 主题名（第三节，默认极简黑白）。
4. 通过 `mindcreate.mjs` 一条命令完成「编码 → 取 theme JSON → 落库」（命令见第四节；不传 reqId、不调 generatedDsl）。
5. 从返回拿 chartId（内部留存）、文件链接、缩略图链接，按第六节交付（Markdown 置于链接之后）。

## 六、呈现结果

按 SKILL.md「统一交付内容」与 `references/examples.md` 的交付模板执行：**文件名 + 类型 + 文件链接 + 文件缩略图（图片渲染）**，最后附 Markdown。本线特有要求：

- **Markdown 必须展示，但置于链接之后**：篇幅可能较长，置前会削弱链接可见性。
- **必须在内置浏览器打开文件链接**：拿到返回后，用当前载体的内置浏览器打开**文件链接**（`present_files` 传文件链接，不传缩略图链接），让用户直接在右侧浏览器查看或编辑。
- **必须在新页签打开**：一次只提交当前这一个文件的链接，新文件落在**新页签**，不覆盖、不替换用户此前已打开的其他文件页签。
- **提示语加粗 + 降级**：**仅当内置浏览器确认打开成功时**，另起一段**加粗**输出「**已在右侧浏览器已打开该文件，您可进行查看或编辑→→**」，紧跟文件信息块之后（Markdown 之前）；**内置浏览器不可用 / 打开失败 / 未确认成功**时**省略该句**，改说「可点击链接查看与编辑」，严禁谎称已打开。
- **文件链接与缩略图链接**完整原样输出纯 URL，禁止省略、截断或改写成"点这里"等短文本。
- **AI 点数按返回值决定**：返回中该项存在且大于 0 才展示；思维导图通常为 0，此时不展示、也不必提及。
- **重试上限 2 次**：落库失败后最多再试 1 次（新建重试前先 query 查重）；仍失败即停止写操作，友好告知（Markdown 已生成，可先展示给用户）。计数与查重规则见 `references/errors.md`。
- 提示语示例（打开成功时）："已为你生成思维导图，**已在右侧浏览器已打开该文件，您可进行查看或编辑→→**，也可继续在对话中要求修改内容、结构、主题。"；**打开失败时去掉加粗那句**，只保留"可点击链接查看与编辑，或继续在对话中要求修改内容、结构、主题。"
